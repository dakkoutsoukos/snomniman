## ADR-0001 - `xarray` as the core data container  [ACCEPTED]
**Context.** Near-field data is multi-dimensional with physical coordinates,
per-array units, and rich metadata.
**Decision.** Represent datasets with `xarray`, wrapped by a domain `Dataset`.
**Alternatives.** raw NumPy + ad-hoc dicts (loses labels); a custom array class
(maintenance burden); pandas (not N-D gridded).
**Consequences.** Strong labeled-array foundation; keep `Dataset` a genuine
boundary (do not leak raw xarray through the public API).

## ADR-0002 - Complex optical/mechanical channels + first-class unwrapped phase  [ACCEPTED]
**Context.** s-SNOM/nano-FTIR signals are complex (`s*e^(i*phi)`); amplitude and
phase are two views of one quantity. But unwrapped phase exceeds +/-pi and cannot
be recovered from a complex angle.
**Decision.** Store channels with both amplitude and phase as **complex**;
expose amplitude/phase as derived views. **Unwrapped phase is a first-class
channel** (OHD-4): it may be generated by processing, stored, visualized,
exported, and consumed downstream. Phase is preserved exactly as imported; any
invert/re-reference/unwrap/normalize is an explicit, provenance-recorded
operation, never silent (OHD-6D).
**Consequences.** Readers assemble complex channels on import; unwrapped phase
lives as its own real channel with explicit provenance.

## ADR-0003 - `xarray.Dataset` with per-channel variables  [ACCEPTED]
**Decision.** One variable per channel inside an `xarray.Dataset`; shared
coordinates; not a single array with a `channel` dimension.
**Consequences.** Natural per-channel units/attrs; access via `Dataset` helpers.

## ADR-0004 - Raw immutability; non-mutating operations  [ACCEPTED]
**Decision.** Loaded raw data is never mutated; every step returns a new `Dataset`.
**Consequences.** Trivially correct provenance and replay. Implementation
refinement (no human input): logical immutability via copy-on-write + intermediate
caching, handled in the implementation phases.

## ADR-0005 - Processing as serializable steps over a provenance DAG  [ACCEPTED]
**Context.** We need transparent history, batch, reproducibility, AND multi-input
workflows (sample/reference normalization, background subtraction, calibration
inputs, stitched scans).
**Decision (OHD-2 resolved).** Each operation is a `ProcessingStep` (stable
`step_id` + `version` + JSON params + `apply`). Provenance is a **DAG**: a step may
take multiple named inputs, each resolving to another `(RawSource + sub-graph)`.
The DAG is serializable and replayable. This is the official provenance
architecture.
**Alternatives.** Single-source linear chain - rejected: cannot represent the
multi-input workflows above.
**Consequences.** Steps keep params JSON-serializable; a registry maps ids to
classes; the serialized form records the full input graph.

## ADR-0006 - Reader **registry**, not a plugin system  [ACCEPTED]
**Decision.** A registry maps format ids to readers and sniffs files to dispatch;
adding a format = implement one reader interface + register it. Use content-based
sniffing and encode format+version in the reader id (engineering refinement).
**Consequences.** Easy in-tree extension; revisit with a new ADR if third-party
plugins are ever needed.

## ADR-0007 - GUI: PySide6 + PyQtGraph; matplotlib for static export  [ACCEPTED]
**Decision.** PySide6 + PyQtGraph for the interactive app; matplotlib for static
vector export. Backend stays Qt-free (Rule 4). `viz` is scoped to display-ready
data, not a unified scene-graph abstraction.

## ADR-0008 - Lightweight unit metadata now; defer `pint`  [ACCEPTED]
**Decision.** Track units as explicit per-array metadata with canonical
conventions and explicit conversion helpers; defer `pint`/`pint-xarray` behind a
chokepoint. Mind the nonlinear wavenumber<->wavelength conversion.

## ADR-0009 - Persistence: Zarr canonical store; vendor reads via readers  [ACCEPTED]
**Context.** We must persist derived datasets and reproducibility artifacts, and
decide the project's relationship to raw microscope files.
**Decision (OHD-3 resolved).** **Canonical project storage is Zarr** (complex-native,
chunked, JSON attrs - suits large cubes + rich metadata + the DAG). **Vendor
files are read by format-specific readers** (HDF5-based vendor files via h5py);
vendor formats are independent of the project store. Provenance/project metadata
serialize to **JSON**. The working project **references external raw files by
path + sha256** plus a manifest; raw files are **never copied or modified**. A
self-contained export bundle (raw + manifest + derived results) comes later.
**Alternatives.** netCDF - rejected: classic netCDF cannot store complex.
**Consequences.** One coherent internal store; relink story for moved raw files
(relative path + hash + size).

## ADR-0010 - Name SNOMNIMAN; package `snomniman`; `src/` layout  [ACCEPTED]
**Context.** Need a distinct, memorable, collision-free name (a PyPI `snompy`
exists for s-SNOM *modeling*).
**Decision (OHD-1 resolved).** Project name **SNOMNIMAN**; Python package and
repository **snomniman**; `src/`-layout. The provisional name `snom` is
**rejected** and the package has been renamed to `snomniman` throughout the repo.
**Consequences.** Memorable, unique, clearly SNOM-related; no further rename.

## ADR-0011 - Python >= 3.11; uv + ruff + mypy + pytest  [ACCEPTED]
**Decision.** Target Python >= 3.11 (works on the installed 3.13); manage with
uv; lint/format with ruff; type-check with mypy (strict); test with pytest.
**Consequences.** `uv` must be installed on this machine (currently absent).

## ADR-0012 - First reader: a real neaSNOM imaging dataset; vendor-extensible  [ACCEPTED]
**Context.** SNOMNIMAN replaces neaPLOT (neaspec/attocube instruments).
**Decision (OHD-9 resolved).** The **first reader target (Phase 1) is a real
neaSNOM imaging dataset**, used as the initial architecture-validation target.
The reader interface is vendor-agnostic; parsing is validated against real files
(Rule 6) and unknown header fields are preserved verbatim. Future modalities
(spectra, hyperspectral, approach curves) remain in scope.
**Consequences.** Fast path to parity; other modalities/vendors via new readers.

## ADR-0013 - Full reproducibility and traceability in provenance  [ACCEPTED]
**Context.** Reproducibility depends on more than parameters.
**Decision (OHD-5 resolved).** SNOMNIMAN records enough to completely reconstruct
and audit a workflow: **data sources, the provenance graph, processing steps,
processing parameters, software versions, and operation versions**. Each
`StepRecord` declares `deterministic`.
**Clarification.** Version capture aids reproducibility/debugging; bit-identical
results are guaranteed only for steps declared deterministic on a matching
environment, otherwise results reproduce to a documented numerical tolerance.

## ADR-0014 - Scientific conventions are explicit, in metadata, with canonical values  [ACCEPTED]
**Context.** Implicit conventions silently corrupt results.
**Decision (OHD-6 resolved).**
- **6A:** scientific conventions are stored **in metadata**, explicit not assumed.
- **6B:** **canonical spatial/length unit = nanometers (nm)** (x, y, s, z, opd).
  Original units are preserved in metadata; conversions are recorded in provenance.
- **6C:** **canonical coordinate convention: origin = lower-left, x increases
  right, y increases upward.** Vendor coordinate systems are preserved in
  metadata; transformations are explicit.
- **6D:** **phase is preserved exactly as imported**; no silent invert,
  re-reference, unwrap, or normalize - all such operations are explicit and
  recorded in provenance.
**Consequences.** Conventions travel with each dataset and are auditable.

## ADR-0015 - Phase 1 is a thin vertical slice  [ACCEPTED]
**Decision.** Phase 1 is end-to-end and narrow: one real neaSNOM imaging reader
-> `Dataset` (with Metadata + Provenance schemas) -> golden-file tests, validating
the architecture on a real file. No GUI, no advanced processing, no visualization
beyond what validates the slice.
**Consequences.** `roadmap.md` is ordered accordingly; Phase 1 is gated only on
sample data.

## ADR-0016 - Metadata and calibration corrections are provenance-tracked operations  [ACCEPTED]
**Context.** A wavenumber recalibration or phase-reference change alters results.
**Decision (OHD-7 resolved).** Metadata edits and calibration corrections are
**provenance-tracked operations**. Silent mutation of scientific metadata is not
permitted.
**Consequences.** "Reproduce from raw + provenance" stays true even across
metadata/calibration corrections.

## ADR-0017 - Hybrid dispatch: DataKind + Capabilities  [ACCEPTED]
**Context.** A closed enum is brittle for operation dispatch; a pure capability
model is less human-legible.
**Decision (OHD-8 resolved).** **Hybrid model.** `DataKind` provides human-facing
dataset classification; **capabilities** (which named axes/channels a dataset
has) determine which operations are supported. Operations declare capability
requirements; `DataKind` drives UX and defaults.
**Consequences.** New modalities add capabilities without enum-driven core edits,
while users still see a clear dataset type.
