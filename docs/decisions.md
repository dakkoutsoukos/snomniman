# Decisions (ADR log)

**Status:** Living document - **Last updated:** 2026-06-29 (ADR-0027: project persistence + data/measurement export)

Architecture Decision Records, lightweight. Each entry: context -> decision ->
alternatives -> consequences -> status. New major decisions are appended here in
the same commit that implements them (Rule 3).

**Status legend (ASCII):** `[ACCEPTED]` settled - `[DEFERRED]` postponed, no
decision needed yet - `[SUPERSEDED]` replaced by a later ADR.

**All Outstanding Human Decisions (OHD-1..9) are now resolved** - see "Decision
Closure" at the bottom. No human decisions remain open.

## ADR-0001 - `xarray` as the core data container  [ACCEPTED]
**Context.** Near-field data is multi-dimensional with physical coordinates,
per-array units, and rich metadata.
**Decision.** Represent datasets with `xarray`, wrapped by a domain `Dataset`.
**Alternatives.** raw NumPy + ad-hoc dicts (loses labels); a custom array class
(maintenance burden); pandas (not N-D gridded).
**Consequences.** Strong labeled-array foundation; keep `Dataset` a genuine
boundary (do not leak raw xarray through the public API).

## ADR-0002 - Complex optical/mechanical channels + first-class unwrapped phase  [ACCEPTED]
**Context.** s-SNOM/nano-FTIR signals are complex (`s*e^(i*phi)`); amplitude and
phase are two views of one quantity. But unwrapped phase exceeds +/-pi and cannot
be recovered from a complex angle.
**Decision.** Store channels with both amplitude and phase as **complex**;
expose amplitude/phase as derived views. **Unwrapped phase is a first-class
channel** (OHD-4): it may be generated by processing, stored, visualized,
exported, and consumed downstream. Phase is preserved exactly as imported; any
invert/re-reference/unwrap/normalize is an explicit, provenance-recorded
operation, never silent (OHD-6D).
**Consequences.** Readers assemble complex channels on import; unwrapped phase
lives as its own real channel with explicit provenance.

## ADR-0003 - `xarray.Dataset` with per-channel variables  [ACCEPTED]
**Decision.** One variable per channel inside an `xarray.Dataset`; shared
coordinates; not a single array with a `channel` dimension.
**Consequences.** Natural per-channel units/attrs; access via `Dataset` helpers.

## ADR-0004 - Raw immutability; non-mutating operations  [ACCEPTED]
**Decision.** Loaded raw data is never mutated; every step returns a new `Dataset`.
**Consequences.** Trivially correct provenance and replay. Implementation
refinement (no human input): logical immutability via copy-on-write + intermediate
caching, handled in the implementation phases.

## ADR-0005 - Processing as serializable steps over a provenance DAG  [ACCEPTED]
**Context.** We need transparent history, batch, reproducibility, AND multi-input
workflows (sample/reference normalization, background subtraction, calibration
inputs, stitched scans).
**Decision (OHD-2 resolved).** Each operation is a `ProcessingStep` (stable
`step_id` + `version` + JSON params + `apply`). Provenance is a **DAG**: a step may
take multiple named inputs, each resolving to another `(RawSource + sub-graph)`.
The DAG is serializable and replayable. This is the official provenance
architecture.
**Alternatives.** Single-source linear chain - rejected: cannot represent the
multi-input workflows above.
**Consequences.** Steps keep params JSON-serializable; a registry maps ids to
classes; the serialized form records the full input graph.

## ADR-0006 - Reader **registry**, not a plugin system  [ACCEPTED]
**Decision.** A registry maps format ids to readers and sniffs files to dispatch;
adding a format = implement one reader interface + register it. Use content-based
sniffing and encode format+version in the reader id (engineering refinement).
**Consequences.** Easy in-tree extension; revisit with a new ADR if third-party
plugins are ever needed.

## ADR-0007 - GUI: PySide6 + PyQtGraph; matplotlib for static export  [ACCEPTED]
**Decision.** PySide6 + PyQtGraph for the interactive app; matplotlib for static
vector export. Backend stays Qt-free (Rule 4). `viz` is scoped to display-ready
data, not a unified scene-graph abstraction.

## ADR-0008 - Lightweight unit metadata now; defer `pint`  [ACCEPTED]
**Decision.** Track units as explicit per-array metadata with canonical
conventions and explicit conversion helpers; defer `pint`/`pint-xarray` behind a
chokepoint. Mind the nonlinear wavenumber<->wavelength conversion.

## ADR-0009 - Persistence: Zarr canonical store; vendor reads via readers  [ACCEPTED]
**Context.** We must persist derived datasets and reproducibility artifacts, and
decide the project's relationship to raw microscope files.
**Decision (OHD-3 resolved).** **Canonical project storage is Zarr** (complex-native,
chunked, JSON attrs - suits large cubes + rich metadata + the DAG). **Vendor
files are read by format-specific readers**; vendor formats are independent of
the project store. Provenance/project metadata serialize to **JSON**. The working
project **references external raw files by path + sha256** plus a manifest; raw
files are **never copied or modified**. A self-contained export bundle (raw +
manifest + derived results) comes later.
**Alternatives.** netCDF - rejected: classic netCDF cannot store complex.
**Consequences.** One coherent internal store; relink story for moved raw files
(relative path + hash + size).
**Note (2026-06-23):** the Phase 1 neaSNOM reader targets the **GSF
measurement-directory format** (Gwyddion Simple Field), not HDF5. `h5py` is
retained in `pyproject.toml` for future HDF5-based vendor formats. See
`docs/measurement-discovery.md`.

## ADR-0010 - Name SNOMNIMAN; package `snomniman`; `src/` layout  [ACCEPTED]
**Context.** Need a distinct, memorable, collision-free name (a PyPI `snompy`
exists for s-SNOM *modeling*).
**Decision (OHD-1 resolved).** Project name **SNOMNIMAN**; Python package and
repository **snomniman**; `src/`-layout. The provisional name `snom` is
**rejected** and the package has been renamed to `snomniman` throughout the repo.
**Consequences.** Memorable, unique, clearly SNOM-related; no further rename.

## ADR-0011 - Python >= 3.11; uv + ruff + mypy + pytest  [ACCEPTED]
**Decision.** Target Python >= 3.11 (works on the installed 3.13); manage with
uv; lint/format with ruff; type-check with mypy (strict); test with pytest.
**Consequences.** `uv` must be installed on this machine (currently absent).

## ADR-0012 - First reader: a real neaSNOM imaging dataset; vendor-extensible  [ACCEPTED]
**Context.** SNOMNIMAN replaces neaPLOT (neaspec/attocube instruments).
**Decision (OHD-9 resolved).** The **first reader target (Phase 1) is a real
neaSNOM imaging dataset**, used as the initial architecture-validation target.
The reader interface is vendor-agnostic; parsing is validated against real files
(Rule 6) and unknown header fields are preserved verbatim. Future modalities
(spectra, hyperspectral, approach curves) remain in scope.
**Consequences.** Fast path to parity; other modalities/vendors via new readers.
**Note (2026-06-23):** the neaSNOM imaging format is **GSF (Gwyddion Simple Field)**:
a measurement **directory** containing one `.gsf` file per channel (O0A..O5P, M0A..M5P,
reference variants, topography) plus a `.txt` parameter file. The reader ingests a
directory, not a single file. See `docs/measurement-discovery.md`.

## ADR-0013 - Full reproducibility and traceability in provenance  [ACCEPTED]
**Context.** Reproducibility depends on more than parameters.
**Decision (OHD-5 resolved).** SNOMNIMAN records enough to completely reconstruct
and audit a workflow: **data sources, the provenance graph, processing steps,
processing parameters, software versions, and operation versions**. Each
`StepRecord` declares `deterministic`.
**Clarification.** Version capture aids reproducibility/debugging; bit-identical
results are guaranteed only for steps declared deterministic on a matching
environment, otherwise results reproduce to a documented numerical tolerance.

## ADR-0014 - Scientific conventions are explicit, in metadata, with canonical values  [ACCEPTED]
**Context.** Implicit conventions silently corrupt results.
**Decision (OHD-6 resolved).**
- **6A:** scientific conventions are stored **in metadata**, explicit not assumed.
- **6B:** **canonical spatial/length unit = nanometers (nm)** (x, y, s, z, opd).
  Original units are preserved in metadata; conversions are recorded in provenance.
- **6C:** **canonical coordinate convention: origin = lower-left, x increases
  right, y increases upward.** Vendor coordinate systems are preserved in
  metadata; transformations are explicit.
- **6D:** **phase is preserved exactly as imported**; no silent invert,
  re-reference, unwrap, or normalize - all such operations are explicit and
  recorded in provenance.
**Consequences.** Conventions travel with each dataset and are auditable.

## ADR-0015 - Phase 1 is a thin vertical slice  [ACCEPTED]
**Decision.** Phase 1 is end-to-end and narrow: one real neaSNOM imaging reader
-> `Dataset` (with Metadata + Provenance schemas) -> golden-file tests, validating
the architecture on a real file. No GUI, no advanced processing, no visualization
beyond what validates the slice.
**Consequences.** `roadmap.md` is ordered accordingly; Phase 1 is gated only on
sample data.

## ADR-0016 - Metadata and calibration corrections are provenance-tracked operations  [ACCEPTED]
**Context.** A wavenumber recalibration or phase-reference change alters results.
**Decision (OHD-7 resolved).** Metadata edits and calibration corrections are
**provenance-tracked operations**. Silent mutation of scientific metadata is not
permitted.
**Consequences.** "Reproduce from raw + provenance" stays true even across
metadata/calibration corrections.

## ADR-0017 - Hybrid dispatch: DataKind + Capabilities  [ACCEPTED]
**Context.** A closed enum is brittle for operation dispatch; a pure capability
model is less human-legible.
**Decision (OHD-8 resolved).** **Hybrid model.** `DataKind` provides human-facing
dataset classification; **capabilities** (which named axes/channels a dataset
has) determine which operations are supported. Operations declare capability
requirements; `DataKind` drives UX and defaults.
**Consequences.** New modalities add capabilities without enum-driven core edits,
while users still see a clear dataset type.

## ADR-0018 - Scientific Description API (`snomniman.describe`)  [ACCEPTED]
**Context.** Several present-day consumers (the Measurement Explorer, publication/
provenance export, future reports, debugging, tests) each need the same structured
answers about a measurement - kind, channels, capabilities, conventions, lineage,
available operations - and were re-deriving them independently. A future AI layer
will need the same context. Rule 7 forbids speculative abstraction, so the
justification must stand on present-day value, not on anticipated AI.
**Decision.** Add a Qt-free backend package `snomniman.describe` that projects the
scientific core (`Dataset`, `Metadata`, the provenance DAG, `RawSource`) and the
processing registry into structured, typed, JSON-serializable *descriptors*. It is
strictly **read-only**: no scientific computation, no mutation, no provenance
bypass. It depends on `core` + `processing` only (the `pipeline` tier) and is
consumed by `gui`, `batch`, and the future `ai` layer - **not** by `viz` (which
stays `core`-only). It is named for what it does today (description/introspection);
it is explicitly **not** a "Knowledge Layer" / "Reasoning Layer" (it does no
reasoning) and it excludes GUI/Explorer state and all AI-specific concepts. AI is
one future client of the same API.
**Alternatives.** (a) Defer until the first AI feature defines the need - rejected:
the consumers and the duplication exist *today*. (b) Build a broader AI-oriented
"Knowledge Layer" - rejected as speculative (Rule 7) and mis-named. (c) Put
introspection on `Dataset` itself - rejected: the operation catalogue needs
`processing`, which `core` must never import (it would invert the dependency graph).
**Consequences.** One canonical, tested source of structured measurement facts; the
Explorer's provenance view already consumes it (backend owns the facts, GUI owns the
words). Per-dataset operation *applicability* stays shallow until steps declare
required capabilities as data - a separate, future refinement to the processing
engine, deliberately **not** done here. `viz` keeps its own figure-provenance record
(it is below `describe` in the stack). Full detail: `docs/description-api.md`.

## ADR-0019 - Scientific Diagnostics Engine (`snomniman.diagnostics`)  [ACCEPTED]
**Context.** A researcher opening a measurement wants objective quality facts at a
glance - global tilt, height range, dynamic range per channel, invalid-pixel counts,
which operations apply. These are *computed* observations, not projections of stored
metadata, so `describe` (which performs no computation, ADR-0018) cannot provide them,
and they are not *transformations*, so they are not `processing` steps either. A future
AI Scientist will also need verified facts to reason over rather than inferring them
from raw arrays. Rule 7 requires a present-day consumer, not an AI justification.
**Decision.** Add a Qt-free backend package `snomniman.diagnostics` that **computes**
deterministic, reproducible, JSON-serializable facts about a dataset: per-channel
statistics, topography slope/roughness/height range, optical harmonic amplitude +
decay, and per-operation structural applicability. Its present-day consumer is the
Explorer's **Diagnostics panel** (Rule 9); the AI is a later, second consumer. It
depends on `core` + `processing` only, never mutates a dataset, and adds nothing to the
provenance DAG (reading a diagnostic is not an operation). It is the **sibling** of
`describe`, **not** an input to it: `describe` stays a pure projection and consumers
compose the two. To make applicability an honest fact, `ProcessingStep` gains a declared
`required_capabilities` class field (implementing the ADR-0017 hybrid-dispatch intent
the code already documented); `image.plane_level` declares `SPATIAL_2D`.
**Alternatives.** (a) Fold diagnostics into `describe` - rejected: it would break
ADR-0018's no-computation contract. (b) Ship backend-only for the future AI - rejected
as the Rule-7 speculative-infrastructure trap; it earns its place via the Explorer
today. (c) Compute an "SNR" and clipping/drift metrics now - rejected (Rule 6): SNR
needs a noise model or signal-free region, clipping needs an ADC limit often absent from
metadata, and single-image drift is ill-posed. The **amplitude-decay ratio** (a
convention-free proxy) and **invalid-pixel counts** are reported instead; the others are
deferred, not guessed.
**Consequences.** One canonical, tested source of computed measurement facts, consumed
by the Explorer today and the AI later; the AI reasons over validated observations
instead of pixels. `ProcessingStep` now carries declared capabilities, so applicability
is data-driven across the GUI and future layers. The engine is the first realization of
the project compass: *every scientific operation and observation is deterministic; only
interpretation is left to reviewable AI.* Full detail: `docs/diagnostics-engine.md`.

## ADR-0020 - First AI capability: the Scientific Briefing (`snomniman.ai`)  [ACCEPTED]
**Context.** With the deterministic foundation complete (Dataset, provenance, processing
engine, Description API, Diagnostics Engine), the AI finally has something meaningful and
*safe* to consume. The first AI capability should not perform or recommend processing; it
should help a researcher **understand** what they have loaded ("tell me about this
measurement"). Two hard project lines apply: a new major dependency needs an ADR, and AI
must never become a silent scientific authority.
**Decision.** Add a Qt-free package `snomniman.ai` whose first capability is **measurement
orientation**. `build_briefing(dataset)` composes `describe` (structure) + `diagnostics`
(computed facts) into a `Briefing`: three deterministic **fact** sections (Summary,
Observations, Enables), each statement tagged with its source layer, plus an optional
natural-language **interpretation** rendered by a `NarrativeProvider`. The briefing is
read-only text - it never mutates the Dataset and adds nothing to the provenance DAG. It
depends only on `describe` + `diagnostics` + `core`; it never touches raw arrays, Qt, or
Explorer state. The present-day consumer is the Explorer's read-only **Briefing** panel
(Rule 9). Grounding is by construction: a provider receives only the facts payload
(`BriefingContext`), the prompt forbids invention, and the briefing stores that payload for
audit. **No model SDK is bundled** (zero new dependency this milestone): only the provider
seam (protocol + grounded prompt builder + a network-free mock). A concrete provider
arrives later as an *optional* extra, lazy-imported, never required for the backend or CI.
Two principles are made permanent in `CLAUDE.md`: (1) the AI may reason only over
deterministic facts SNOMNIMAN produced, never the primary interpreter of raw data when a
deterministic algorithm exists; (2) every AI feature has a useful deterministic fallback -
AI enhances understanding, never gates it.
**Alternatives.** (a) Start with processing recommendations - rejected: higher risk, and
orientation is the smaller, safer, immediately-useful first step. (b) A chat interface -
rejected: this is a briefing, not a chatbot (no input box, history, or agent behaviour).
(c) Bundle a model SDK now - rejected: not needed for the deterministic briefing, would add
a major dependency and a network/key requirement to CI; deferred to an optional extra
behind the provider protocol. (d) Fold AI into `describe`/`diagnostics` - rejected: AI is a
non-deterministic renderer; it belongs above the deterministic layers, consuming them.
(e) Claim per-sentence narrative traceability - rejected as overclaiming; grounding is by
construction and auditable against `context`, but free-text is not machine-verified
sentence-by-sentence (a candidate future milestone).
**Consequences.** Everything built over the prior milestones now has a natural AI consumer,
and the AI reasons over validated facts instead of pixels. The app is fully useful with no
API key (facts always render). The seam makes adding a real provider a small, isolated,
optional change. The deterministic core remains the single source of truth. Full detail:
`docs/ai-scientist-v1.md`.

## ADR-0021 - Generic, registry-driven Processing Workspace (no per-operation GUI)  [ACCEPTED]
**Context.** The processing engine grew a vocabulary (`image.plane_level`,
`reference_normalize`, `phase_unwrap`, `crop`), but the Explorer only knew how to preview
plane leveling - its Process panel was hand-wired to one operation
(`_on_preview_requested(channel, order)`). Adding each operation to the GUI separately would
make the Explorer a menu labyrinth and couple GUI code to each algorithm, violating Rule 2
(no parallel implementations) and Rule 9 (every GUI feature must earn its place). The
operations are already first-class in the registry, the Description API, and the Diagnostics
Engine; the GUI should *consume* those, not re-encode operation knowledge.
**Decision.** Replace the operation-specific Process panel with one generic, registry-driven
**Processing Workspace** that exposes *every* registered `ProcessingStep`. All of it is a
projection of existing layers: discovery/grouping from `describe_operations()`; availability
and "why unavailable" from the Diagnostics Engine's `operation_applicability`; the parameter
form generated from each `ParameterSpec`; preview by applying the step to the live dataset
(the engine is purely functional) and **diffing** the derived dataset against the current one
to report, generically, what changes and what stays; provenance preview = the real
`StepRecord` Accept will commit. To let a generic form pick the right control without GUI-side
scientific knowledge (Rule 4), `ParameterSpec` gains two optional, declarative UI hints:
`choices` (a fixed enum, also enforced by `validate()`) and `channel_role`
(`any`/`real`/`complex`, marking a `str` param as naming a channel of that kind). The
Description API's `OperationParameter` projects both. Adding a new operation now requires
only: implement, register, declare `param_specs` + `required_capabilities` - the Explorer
provides discoverability, parameter editing, preview, provenance preview, accept/cancel, and
history with **no new GUI code**.
**Alternatives.** (a) Keep wiring each operation by hand - rejected: O(operations) GUI code,
drift, and a growing menu (Rule 2/9). (b) A name heuristic in the GUI ("a `str` param called
`channel` lists real channels") - rejected: it puts scientific knowledge (which kind each
operation needs - real for leveling, complex for unwrap) in GUI code (Rule 4) and is fragile.
(c) A new GUI abstraction layer for operation forms - rejected as premature generalization
(Rule 7): the registry + `ParameterSpec` + the Qt-free presenter already carry everything; a
new layer is unnecessary. (d) Compute "what will change" from per-operation declarations -
rejected: diffing the actual preview against the current dataset is truthful and fully generic
(no per-operation upkeep). (e) Build a multi-input picker now - deferred (Rule 7): no
registered operation is multi-input yet; the single-input `{"primary": ds}` convention covers
every current step, and the form gains an auxiliary-input picker when a real multi-input
operation exists.
**Consequences.** Operation-specific processing UI is permanently eliminated; the next
operation (e.g. `image.line_flatten`) needs essentially no UI work. `ParameterSpec` now also
declares display-affecting hints, but they never change a computed result (pure UI/validation),
and the dataset-dependent channel filtering stays in the Qt-free presenter, so the widgets
remain thin and the backend Qt-free (Rule 4). The change is additive: existing specs and the
plane-level workflow are unchanged (the latter now runs *through* the generic interface, with
its tests rewritten accordingly). Full detail: `docs/processing-engine.md` ("Processing
Workspace") and `docs/measurement-explorer.md` (Section 7).

## ADR-0022 - AI Suggested Next Steps are deterministic, not LLM-generated  [ACCEPTED]
**Context.** With the Briefing (orientation) and the generic Processing Workspace shipped,
the AI Scientist's next capability is *workflow guidance*: a ranked "Suggested Next Steps"
that proposes which registered operation to apply, why, and hands it to the Workspace to
preview. The open question was who *generates* the recommendations: a deterministic engine
over the existing facts, or an LLM (constrained to applicable operations). The product
requirements are strict - every recommendation must cite deterministic evidence and must
never suggest an unavailable or already-applied operation, contradict the diagnostics or
provenance, or invent data.
**Decision.** The recommendations are produced **deterministically** by `snomniman.ai`
(`recommend_workflow -> WorkflowSuggestions`), composing the Description API + Diagnostics
Engine (applicability, topography tilt, channel states, provenance). One self-guarding rule
per operation emits a `Recommendation` only when the operation is applicable, not already
applied, and supported by a concrete deterministic observation; v2 ships two rules (plane
level when a measured tilt dominates the *signal* topography; reference normalize when
references exist and signals are raw). Each recommendation carries `step_id` + pre-filled
`params`, a heuristic `confidence` in [0,1] (a deterministic *priority* from evidence
strength - **not** a probability; shown as a strength tier), a `rationale`, source-tagged
`evidence`, and an `expected_outcome`. The Explorer's AI Scientist panel renders them as
cards with a Preview button that hands off to the generic Workspace (no AI-specific
execution path). The engine never executes; the deterministic processing engine alone
performs operations, via an explicit, provenance-recorded Accept. The `NarrativeProvider`
seam remains for optional prose, but a provider may only *phrase* suggestions, never choose
or rank them.
**Alternatives.** (a) LLM-generated recommendations filtered against applicability - rejected:
it violates permanent rule 1 (don't ask an LLM to infer what diagnostics can establish - the
tilt is already computed) and makes the safety rules *hopeful* (a prompt-constrained model can
still hallucinate an unavailable step) rather than *structural* (a generator built from
applicability cannot). It would also have no offline fallback (permanent rule 2). (b) A new
recommendation layer/engine outside `ai` - rejected (Rule 7): the AI Scientist is exactly the
"help me understand and decide" layer, and it already composes describe + diagnostics. (c)
Confidence as a probability - rejected as overclaiming (honesty about kind): it is a documented
heuristic priority, surfaced as strong/moderate/tentative. (d) Auto-apply or a chat agent -
rejected: the AI proposes; the researcher disposes through the Workspace; nothing is silent.
A small **correctness fix** rode along: `diagnostics.topography_diagnostics` now reports the
*signal* topography (prefers canonical `Z`), never a reference height channel (`R_Z*`), which
also corrects the Briefing's topography facts.
**Consequences.** The "open measurement -> briefing -> suggested steps -> preview -> accept"
experience the workspace was built for now exists, and it is safe by construction: the AI
cannot recommend something the engine would refuse. The suggestions are fully available
offline, structured/inspectable (JSON), and carry their grounding for audit. They evolve as
the deterministic vocabulary grows (new rules, not AI code). Full detail:
`docs/ai-scientist-v1.md` ("Suggested Next Steps").

## ADR-0023 - Scientific Reasoning Rule Engine: recommendations as registered rules  [ACCEPTED]
**Context.** ADR-0022 shipped deterministic Suggested Next Steps as two ad-hoc functions
(`_recommend_plane_level`, `_recommend_reference_normalize`). To grow this into "how an
experienced SNOM researcher thinks" - and to keep the deterministic layer the scientific
authority as the vocabulary grows - the recommendation logic should be first-class,
individually testable, explainable, and extensible: a registry of rules where "every new
operation simply contributes another rule." This also crystallised a third permanent AI
principle (added to `CLAUDE.md` with a motto): *deterministic systems choose whenever a
deterministic rule exists; AI adds explanation/prioritization/communication, not scientific
authority.*
**Decision.** Add a **Scientific Reasoning Rule Engine** inside `snomniman.ai` (not a new
subsystem): `reasoning.py` defines `ReasoningRule` (declarative: `rule_id`, `step_id`,
`summary`, `prerequisite_steps`, `excluded_steps`, and a deterministic
`evaluate(ctx) -> RuleOutcome | None`), a `ReasoningContext` (the describe + diagnostics
projections a rule may use), and a rule registry mirroring the processing-step registry.
`recommend.py` becomes the engine: it evaluates every registered rule, enforces the
universal guards (applicable + not-already-applied) so rules contain only the *scientific*
trigger, honours prerequisites (suppress-until-applied -> natural cross-iteration sequencing)
and exclusions (drop the weaker of a mutually-excluded pair), and ranks by confidence. The
recommendation data types move to `report.py`; `Recommendation` gains `rule_id` (full
traceability) and `considerations` (deterministic caveats / "possible downside"). Evidence is
source-tagged across `diagnostics`/`description`/`provenance`/`metadata`, and rules emit
interaction-aware, provenance-sourced evidence (e.g. reference-normalize notes completed
leveling).
**Alternatives.** (a) Keep the two functions - rejected: not individually testable as units,
no explicit triggers/relationships, no clean extension point for the explainability the
project needs. (b) Build a full dependency/ordering **solver** with rich
prerequisite/exclusion graphs now - rejected (Rule 7 + the project's own "abstractions need a
present consumer"): today's four operations have no hard prerequisites or exclusions, so a
solver would be machinery without a consumer. The cheap, tested *mechanism* is included
(foreseeable consumer; matches the schema), but the shipped rules declare no relationships,
and suppress-until-applied already yields sequencing. (c) Ship phase-unwrap / crop rules to
"complete" the set - rejected as ungrounded: phase-unwrap needs a *validated* wrapping
diagnostic (Rule 6) and crop is user-intent-driven; recommending either without deterministic
evidence violates the engine's own contract. Both are documented as deferred. (d) Let an LLM
generate/order rules - rejected by AI rule 3 (this is the authority layer; the LLM phrases,
never chooses).
**Consequences.** Recommendations are now explainable to the trigger ("why was this
recommended?" answers from deterministic facts incl. provenance), individually testable, and
extended by registering one rule (no engine/GUI change). The public API
(`recommend_workflow`, `Recommendation`, `WorkflowSuggestions`, ...) is unchanged - the
refactor is internal. The deterministic layer is unambiguously the scientific authority; the
future LLM is its interpreter. Full detail: `docs/scientific-reasoning.md`.

## ADR-0024 - The Knowledge Center: an integrated scientific knowledge base  [ACCEPTED]
**Context.** SNOMNIMAN now contains substantial scientific knowledge (concepts, operations,
diagnostics, provenance, AI reasoning), but a researcher must know the science already to
use it. The opportunity: teach the science *inside* the product - and, in doing so, give the
(future) AI a curated base to ground explanations in rather than improvising. This must not
become a generic doc browser or duplicate the README, and - per the project maxim - its
content must be accurate and defensible, never padded to hit a count.
**Decision.** Add a Qt-free leaf package `snomniman.knowledge`: structured, queryable
**articles** (frozen `Article` value objects) rather than static markdown. Each has a
dot-namespaced id (`concept.*` / `operation.*` / `diagnostic.*` / `ai.*`), required
title/summary/explanation, and optional fields (scientific/mathematical background, when-to-use,
common mistakes, references, and cross-references to related concepts/operations/diagnostics).
A `query.py` provides lookup/search/by-category and id-convention resolvers
(`article_for_operation(step_id)` etc.). The Explorer gains a **Knowledge** panel (browse tree
+ search + a `QTextBrowser` article view with clickable internal links), and other panels gain
**"Learn more"** deep-links: the Processing Workspace (operation -> its article) and AI Scientist
recommendation cards (operation -> its article), routed through the window via
`article_for_operation`. AI integration today is the deep-link (curated content, not model
prose); a future provider grounds its explanations in the base. Two integrity guarantees keep
the base honest: `integrity_problems()` (no dangling cross-references) and a test that **every
registered ProcessingStep has an operation article** (no drift from the code).
**Alternatives.** (a) Ship `/docs` markdown in a viewer - rejected: not structured/queryable,
not contextually linkable to objects, would duplicate README/docs. (b) Let the AI generate
explanations on demand - rejected by the AI rules: explanations would be improvised and
unverifiable; the curated base is the canonical teaching, the model only phrases it. (c) Exhaustively
document every concept now - rejected (the maxim): the library is an *initial, curated* set,
grown only as articles can be made accurate; a no-drift test enforces operation coverage without
forcing breadth elsewhere. (d) Fold articles into `describe`/`ai` - rejected: teaching content is
a distinct responsibility (curated prose, not a projection of a dataset or a reasoning rule);
it earns its own leaf package, consumed by `gui` (and a future narrator).
**Consequences.** A researcher can click "Learn more" on an operation or a recommendation and
read accurate, interconnected teaching without leaving the app; the same base will ground the
future AI narrator. Adding an operation now also calls for an article (enforced). The package is
a clean leaf (no internal deps), so it does not entangle the architecture. Full detail:
`docs/knowledge-center.md`.

## ADR-0025 - Governance: Beta Readiness as the product roadmap; the Scientific Validation Phase as the scientific methodology  [ACCEPTED]
**Context.** Foundational development is complete (architecture, Explorer, processing engine,
Description/Diagnostics/AI/Knowledge layers - ADR-0018..0024). The bottleneck is no longer
software architecture; it is **deciding which capabilities deserve implementation** - which
workflow gaps actually prevent researchers from replacing neaPLOT, and which scientific
judgments can be automated *and defended*. Without a framework, the project risks drifting back
to speculative feature-by-feature accumulation - exactly what the maxim warns against. This ADR
records **governance, not functionality**: no code, no architecture change, and no existing
scientific rule is altered.
**Decision.** Adopt **two complementary, permanent planning systems** as the decision framework,
and require future work to trace to one of them: (1) the **Product Roadmap** -
[`beta-readiness-v1.md`](beta-readiness-v1.md), a recurring full-workday readiness review that
identifies the validated *workflow gaps* (the neaPLOT switch-back points) and is the authoritative
product backlog; and (2) the **Scientific Validation Phase** -
[`scientific-validation.md`](scientific-validation.md), the permanent methodology by which a
*scientific capability* enters the engine (Scientific Question -> Literature Review -> Candidate
Deterministic Diagnostics -> Analytical -> Synthetic -> Real-data Validation -> Decision ->
Implementation, **last**), with three legitimate Decision outcomes (validate-and-implement /
defer / stop) in which **honest deferral is a success**. Implement only at their intersection
(*needed* and *validated*); a validated capability **extends an existing layer** (diagnostics /
`ai.reasoning` / processing / knowledge), never a new subsystem without its own ADR (Rule 7).
Rename the "Scientific Knowledge Phase" to the **Scientific Validation Phase** (validation, not
accumulation, is the discipline; and "Knowledge" collided with the shipped Knowledge Center).
**Alternatives.** (a) Continue choosing features case-by-case - rejected: drifts toward
unjustified features; the maxim ("two we can defend over four we can't") demands a gate. (b) One
combined roadmap mixing product and science - rejected: they answer different questions ("what do
researchers need?" vs "what can we honestly automate?") under different authorities; conflating
them hides the scientific gate. (c) Keep the "Scientific Knowledge Phase" name - rejected: it
frames the goal as accumulation and collides with `snomniman.knowledge`. (d) Record this only in
the docs, no ADR - rejected: Rule 3 records decisions in `decisions.md`, and this is a permanent
governance decision worth citing (cf. ADR-0015, a process ADR).
**Consequences.** Future contributors learn how capabilities are proposed, validated, and
implemented from two authoritative documents; the validation template + Future Validation Queue
make scientific milestones repeatable; the maxim is operationalized (deferral is a recorded
outcome, not a failure). The Beta Readiness review is re-run per iteration
(`beta-readiness-v2`, ...). No functional change (373 tests unaffected). `CLAUDE.md` ("Planning
and Governance"), `roadmap.md` ("Current driver"), `architecture.md` (Section 10), and `NEXT.md`
are updated to point here. Full detail: `docs/scientific-validation.md`, `docs/beta-readiness-v1.md`.

## ADR-0026 - Harmonic signal-vs-noise classification; discharge ADR-0019's SNR deferral  [ACCEPTED]
**Context.** The first Scientific-Validation study to reach **Outcome 1**
([`harmonic-ranking-analysis.md`](harmonic-ranking-analysis.md), the Candidate-2 milestone of
ADR-0025). The question - "which optical harmonics are signal vs. noise, deterministically?" -
is the Beta Readiness M4 gap and, per ADR-0019, the exact judgment the Diagnostics Engine had
**declined** to make: ADR-0019 reported amplitude/decay but not SNR, because "a true SNR needs a
noise model or a signal-free region, neither available deterministically from a single image."
The study supplies and validates that missing noise model.
**Decision.** Extend the existing `HarmonicAmplitude` descriptor (Rule 7 - no new subsystem) with
a deterministic **signal-vs-noise classification**: per optical harmonic, a **spatial coherence**
(mean lag-1 autocorrelation of the amplitude image; analytical white-noise null), a **single-image
SNR estimate** (Immerkaer 1996 noise sigma), and a conservative label - `signal` / `weak` /
`noise` / `empty` / `unknown`. Thresholds are tied to the SNR=1 (coherence ~0.5) and SNR=0.5
(~0.2) crossovers (calibrated synthetically, not fitted). This **discharges ADR-0019's SNR
deferral** for a *validated single-image estimate under a stated white-noise assumption* - the
Validation Phase working as designed (a deferral lifted when evidence arrived). The fact is
surfaced by the generic Diagnostics panel, the Briefing, and a Knowledge article; **no
`ReasoningRule` is added.**
**Alternatives.** (a) A total-order "informativeness ranking" / "best-harmonic recommendation" -
**rejected**: the structure/SNR metrics conflate near-field with far-field background (real O1
background reads as high-SNR "signal", even outscoring near-field O3), and "best" is the genuine
confinement-vs-SNR expert tradeoff - not a deterministic fact (study §6/§7). (b) Ship a reasoning
rule "use harmonic N" - rejected for the same reason (mirrors phase-unwrap/line-flatten: ship the
fact, decline the judgment). (c) Keep ADR-0019's blanket "no SNR" - rejected: it was conditioned
on the *absence of a validated noise model*, which now exists (recovers true SNR to ~1% on
synthetic data; validated two-sided on real data). (d) Coherence only, no SNR - rejected: the SNR
is the reusable noise-floor primitive Candidate 3 (reference-normalization criteria) consumes.
**Consequences.** The Diagnostics Engine now answers M4 ("which orders are signal vs. noise") with
a fact validated on **both** branches (the bar phase-wrapping could not clear). The single-image
noise-floor estimate is now available for Candidate 3 to reuse rather than re-derive (Rule 7).
Honest scope is preserved: the classification is a noise-floor judgment, **not** near-field-vs-
background nor "best harmonic." 415 tests pass (analytical + synthetic + two-sided real CdO golden
+ briefing/GUI integration); `ruff`, `mypy --strict`, and the Qt-free invariant green.
`diagnostics-engine.md`, `knowledge-center.md`, `scientific-validation.md`, and
`next-scientific-priorities.md` are updated.

## ADR-0027 - Project persistence + data/measurement export; `pipeline -> io`  [ACCEPTED]
**Context.** Beta Readiness Section 3 names three Critical workflow gaps that complete the
research workflow: **C1** (export the processed dataset), **C2** (export measurement numbers),
and **H1** (save/reopen a project - the Phase-4 reproducibility exit criterion). Each is meant to
*expose a capability the backend already has* (the Zarr store, the GSF writer, the provenance DAG,
the measurement engine), not to add a new scientific subsystem. The open design question was where
project persistence lives, because `Project` is documented in `pipeline` (a stub until now) while
the Zarr store lives in `io`, and persisting a project inherently needs that store.
**Decision.** (1) **Project persistence lands in `snomniman.pipeline`** (`Project`,
`save_project`, `load_project`, `project_from_history`) - its constitutionally-documented home. A
project is a **bundle**: a `<name>.snomproj` directory holding one canonical Zarr store per dataset
(reusing `io.write_zarr`/`read_zarr` verbatim) plus a `project.json` manifest (dataset order,
`current_index`, and an **opaque** `session` document). Because each dataset already serializes its
full provenance DAG, the processing history round-trips for free. This adds one acyclic dependency
edge **`pipeline -> io`** (no cycle: `io -> core` only). (2) **GSF channel export lands in `io`**
(`export_channel_gsf`): a single real-valued grid per call (a complex channel as amplitude / phase
/ real), float32, flipped back to GSF top-to-bottom, with a `.provenance.json` sidecar carrying the
serialized DAG (a single GSF file cannot hold a DAG) - mirroring the figure export. (3)
**Measurement CSV export** is Qt-free presenter logic in `gui/export.py` (the `ProfileSet` /
`RegionReport` value objects live in `gui.model`; the numbers come from the validated `viz.measure`
backend) with a provenance header; the widgets only choose a delimiter and a destination.
**Alternatives.** (a) Put `Project` in `io` (no new edge) - rejected: contradicts the constitution's
explicit assignment of `Project` to `pipeline`, and conflates the reproducibility engine with the
reader/writer layer. (b) Put persistence in `io` importing `pipeline.Project` (`io -> pipeline`) -
rejected: a backward edge (io sits below pipeline). (c) Replay derived datasets from the DAG instead
of storing them - deferred: faithful storage of every derivation is the honest, robust choice now
(reproducibility first); the DAG is still fully persisted, so replay remains a future optimization.
(d) A new single-file project format - rejected (Rule 2/7): it would duplicate the Zarr store; a
bundle reuses it. (e) Persistent "Recent Projects" - deferred: it needs a settings store, out of
scope here.
**Consequences.** A researcher can now load -> inspect -> compare -> measure -> process -> **save**
-> close -> **reopen** -> continue, and export publication figures, processed datasets (Zarr,
loss-less / GSF, interchange), and quantitative measurements (CSV / clipboard) - the first complete
end-to-end workflow. Raw immutability and reproducibility are preserved (reopening restores the same
provenance DAG; raw stays read-only). The new `pipeline -> io` edge is recorded in
`architecture.md` (layer graph + Section 3 + Section 10). 447 tests pass (project round-trip incl.
the real CdO measurement, GSF export round-trip, CSV builders, and window save/reopen/export);
`ruff`, `mypy --strict`, and the Qt-free invariant green (pipeline imports io, both Qt-free).

## ADR-0028 - Multi-measurement projects: `Measurement` (a promotion) + `Project` container  [ACCEPTED]
**Context.** Beta Readiness Section 3 names **C3** (open more than one measurement) as the last
Critical workflow gap: a researcher must work on a whole experiment - many independent scans - in
one session without relaunching. The original `Project` (ADR-0027) modeled a *single* measurement's
derivation history (a tuple of datasets, raw first). The load-bearing insight from reading the code:
**that `Project` was already a `Measurement`** - the datasets tuple is one scan's history. So the
correct move is a *promotion*, not a parallel "list of projects" bolted on top.
**Decision.** (1) **Promote the single-measurement `Project` to a new immutable `Measurement`**
(`measurement_id`, `title`, `datasets` history, `current_index`, opaque `session`) and redefine
**`Project` as an ordered collection of `Measurement`s** (+ active `current_index` + opaque
project-level `session`). The dataset-history semantics are unchanged (`datasets[0]` = raw). A
single-measurement project is the common case and behaves like the old model. (2) **Persistence
evolves in place - no second format (Rule 2/7).** Schema `1 -> 2`; the `.snomproj` bundle nests
datasets under `measurements/measurement_NN/datasets/dataset_NN.zarr`; on-disk directory names are
**ordinal** (reflect display order at save) while the **stable id lives in the manifest**, so
reordering/removal never churns paths. **v1 bundles still load**, migrated into a one-measurement
project with the v1 `session` re-homed onto the measurement. (3) **Measurement ids are stable,
project-local, human-readable, and never reused** (`measurement-0001`, ...), assigned by the GUI via
a **persisted monotonic counter** (in the project-level `session`) - **not UUIDs** (ids are never
networked or shared; sequential ids are debuggable). (4) **GUI ownership split (reuses the ADR-0027
materialize-at-save pattern):** a Qt-free `MeasurementSession` holds one measurement's *live* working
state (active view-model, derivation back-stack, captured view + overlay records); the window hosts a
list of sessions + an active index and binds a single set of widgets to the active one. **Switching
captures the outgoing session's view + overlays and restores the incoming one's with no disk reload.**
A **Measurement Manager** dock (list, active marker, Add / Rename / Close) is the primary navigation
tool; the File menu gains New/Close Project and Add/Close Measurement. (5) **Success criterion: a
one-measurement project is indistinguishable from the prior app** - existing single-measurement GUI
tests pass unchanged (the window's `_model`/`_history` became properties delegating to the active
session), the Manager shows a single quiet row, and the "m/n" title appears only when n > 1.
**Alternatives.** (a) A new `Workspace` layer *above* `Project` (a list of projects) - rejected:
contradicts the product model ("a Project *is* a collection of measurements") and ignores that the
existing `Project` was already a `Measurement`; promotion is the smaller conceptual change (Rule 2).
(b) UUID ids - rejected (user direction): project-local, never-shared ids are better as readable
sequential handles; a persisted counter guarantees non-reuse, which keeps them safe as stable handles
for later cross-measurement/batch features. (c) A new project file format - rejected (Rule 2/7):
evolve `.snomproj` (bump schema, nest, migrate v1); keep one format that reuses the Zarr store. (d)
Lazy-load datasets to bound memory at 100+ measurements - **deferred** (Rule 7): unnecessary for
imaging now; the seam (`load_project` / `Measurement`) localizes a future change. Honest known
limitation, not solved speculatively. (e) Mutation methods on the frozen value objects - rejected:
the GUI owns mutable working state and materializes immutable `Measurement`/`Project` snapshots at
save (the ADR-0027 pattern); the value objects stay immutable, the assignment policy (ids) stays in
the GUI.
**Consequences.** A researcher can open many measurements in one session, **switch instantly with
each measurement's state preserved**, process each independently, and **save/reopen the whole
project** with every measurement, derivation history, provenance DAG, active selection, view, and
overlays restored. No new module and **no new cross-layer edge** (reuses `pipeline -> io`);
`Measurement`/`Project` stay Qt-free; raw immutability and reproducibility are intact. The `Project`
value-object shape changed (a deliberate promotion), so the project-store and GUI-session tests were
rewritten and extended (add / switch-preserves-state / close / rename, multi-measurement round-trip,
**v1 migration**). 458 tests pass; `ruff`, `mypy --strict`, and the Qt-free invariant green. Beta
blocker **C3 closed**; this is the architectural foundation for cross-measurement comparison, batch,
and experiment-wide scientific workflows (later phases).

## ADR-0029 - Phase 2B experiment analysis: a read-only `ExperimentModel`; difference views -> 2C  [ACCEPTED]
**Context.** Phase 2A (ADR-0028) made a project a collection of measurements. The next product
question is *how a researcher analyses an **experiment** (many measurements) rather than one* -
compare them, rank them, measure across them. The risk is that "experiment analysis" becomes a
feature dump. The constraint (and the scope the user approved): build **on** the 2A architecture
**read-only**, without introducing multi-input processing or new provenance semantics.
**Decision.** (1) **One new thin, Qt-free presenter, `ExperimentModel`** (`gui/experiment.py`) - the
experiment-level sibling of `ExplorerModel`. It **aggregates only existing capabilities** over the
project's sessions: each measurement's `ExplorerModel` (render / per-pixel values / `viz.measure`
region+line) and the Diagnostics Engine (`diagnose`). It produces experiment-wide view objects - a
browser overview, cross-measurement comparison panes + a combined cursor readout, an experiment
**diagnostics table**, and **cross-measurement statistics** (the same ROI/line evaluated on every
measurement). It **computes no new science and creates nothing** - no datasets, no provenance nodes,
no operations. `diagnose` is cached per dataset (datasets are immutable, so the cache is always
valid). (2) **Reuse, not parallel systems.** The existing `ComparisonView` renders cross-measurement
panes - each pane is rendered by its *own* measurement's model and passed through the viewer's
dict-renderer contract, and the viewer already synchronises zoom/pan/cursor - so **no second
comparison system**. `diagnose` powers the diagnostics table; `viz.measure` powers the stats;
`gui/export.py` gains one `experiment_table_to_csv` builder reusing the existing header style. The
**Measurement Manager becomes the experiment browser** (a summary table + multi-select + Compare),
and a new **Experiment** inspector tab holds the sortable diagnostics + statistics tables. (3)
**Read-only is the guardrail:** Phase 2B creates no datasets, provenance nodes, or processing
operations; if a feature needs the write path it moves to 2C. (4) **Difference Views (the original
Part 2) are deferred to Phase 2C.** They are the one write-path part: they need the first
**multi-input** `ProcessingStep`, new GUI surface to pick a second-measurement input, grid /
coordinate compatibility (refuse on mismatch - resampling/registration is out of scope), **and** they
raise an unresolved provenance-topology question - a difference has **two parents**, but a
`Measurement`'s history is **linear**, so where a two-parent derived dataset lives needs its own
design cycle.
**Alternatives.** (a) Put the aggregation in a backend module (`snomniman.experiment`) - rejected
for now (Rule 7): it has exactly one present consumer (the GUI views); promote it if `batch` later
needs it. (b) A second comparison / diagnostics implementation - rejected: reuse `ComparisonView` +
`diagnose`. (c) Include difference views in 2B - rejected (the split above; user-approved) to keep
the milestone a coherent, releasable read-only layer and not a 5,000-line mega-feature. (d) Compute
`diagnose` eagerly for the browser - rejected: the browser shows only cheap metadata facts; the
diagnose-backed table is lazy (computed when the Experiment tab opens) and cached.
**Consequences.** A researcher can open a multi-measurement project and, entirely read-only, browse
it at a glance, compare measurements side by side with a synchronised view + combined readout, rank
scans by project-wide diagnostics, and evaluate one ROI/line across the whole experiment and export
it (CSV / clipboard). **No backend change, no new cross-layer edge, no provenance / processing
change**; `ExperimentModel` is Qt-free and unit-tested headlessly; raw immutability and the
"one-measurement project feels like the prior app" principle both hold. 478 tests pass; `ruff`,
`mypy --strict`, and the Qt-free invariant green. **Difference datasets / multi-input operations are
Phase 2C** (the two-parent provenance topology resolved there).

## ADR-0030 - Multi-input processing: `InputSpec` + compatibility; arithmetic as the first two-input op  [ACCEPTED]
**Context.** Phase 2C. Researchers need to combine multiple datasets deterministically (difference
images now; sum / ratio / normalized difference later) while preserving provenance and the existing
processing framework. The decisive discovery: the engine and the provenance DAG were **already
multi-input** by original design (OHD-2). ``ProcessingStep.apply`` already takes a ``{name: Dataset}``
mapping and builds ``ProvenanceNode(inputs={name: parent})``; ``serialize_dag``/``deserialize_dag``
already persist multiple **named** parents; ``LineageStep.inputs`` already projects them. So 2C
**generalizes existing seams** rather than building a parallel processing system - and the two-parent
provenance/persistence question that deferred this from 2B simply does not require core changes.
**Decision.** (1) **Declare inputs with `InputSpec`** - the dataset counterpart of ``ParameterSpec``.
``ProcessingStep.input_specs()`` defaults to a single ``"primary"`` slot (so every existing
single-input step is unchanged); a multi-input step overrides it. ``apply`` validates that the
provided inputs exactly match the declared slots. (2) **Compatibility is explicit and enforced.**
``ProcessingStep.check_compatibility(inputs) -> tuple[str, ...]`` (default empty) lists human-readable
reasons two inputs cannot be combined; ``apply`` raises ``ProcessingError`` if non-empty (Rule 4), and
the GUI surfaces the reasons and disables Preview. Incompatible inputs are **refused, never silently
resampled or aligned** - registration/resampling are separate, explicit, future operations
(out of scope). (3) **Ownership: a multi-parent derived dataset lives in the primary (active)
measurement's history.** ``Measurement.datasets`` is an ordered list of derivation snapshots, not a
single-parent chain, so appending a two-parent dataset needs no model change; the dataset carries its
**full** DAG (both parents + both ``RawSource``s) and so persists/reopens with complete provenance via
the existing Zarr store (no persistence change). The secondary input is referenced by provenance, not
owned. (4) **`describe` gains an input-slot projection** (``OperationInputSlot`` on
``OperationDescription``) so a generic consumer builds the right dataset picker per slot. (5) **The
first multi-input operation is a general two-input ``image.arithmetic``** (modes ``a_minus_b`` /
``b_minus_a`` / ``absolute_difference``; extensible to sum/ratio/normalized difference via the same
enum), **not** a hardcoded "difference" - it operates on a channel's real value view (amplitude for a
complex channel; phase differencing is excluded as cyclic/re-referencing). (6) **GUI:** the Processing
Workspace renders a dataset picker per non-primary slot (candidates supplied by the window, which owns
the project), through the **same** Preview -> Accept flow; the result appends to the active measurement.
Single-input operations render exactly as before (no picker).
**Alternatives.** (a) A parallel multi-input engine - rejected: the engine + DAG were already
multi-input; generalize, don't duplicate. (b) A new "results" collection or a derived *measurement*
for two-parent datasets - rejected: a parallel ownership abstraction; the primary measurement's
history plus the dataset's own DAG already suffice. (c) Hardcode a ``difference`` operation - rejected
(user refinement): a general arithmetic op + mode enum lets future combinations extend one operation
rather than spawning new step types. (d) Declarative compatibility (a ``must_match`` field on
``InputSpec``) - deferred (Rule 7): a per-op method is enough for the first op; extract it when a
second multi-input op shares the rules. (e) Silently resample/align to force matching grids - rejected
(scientific honesty, OHD-6): refuse with a clear reason instead.
**Consequences.** A researcher can open a project, pick two compatible datasets, create a deterministic
difference, inspect its two-parent provenance, save and reopen it with provenance intact, continue
processing it, and export it - all through the existing Workspace, provenance, persistence, and export,
with no parallel system. Single-input operations and previously-saved projects are unaffected (the
defaults). The change adds one declarative type (``InputSpec``), one method (``check_compatibility``),
one ``describe`` projection, the GUI pickers, and the ``image.arithmetic`` operation (with a Knowledge
article, so the no-drift invariant holds). 500 tests pass; ``ruff``, ``mypy --strict``, and the Qt-free
invariant green. This establishes the long-term foundation for every future multi-input operation
without another redesign.
